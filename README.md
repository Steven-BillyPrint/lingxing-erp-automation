# ERP 自动化桌面程序

这是面向 Windows 的领星 ERP 自动化桌面程序。日常入口是 PySide6 图形界面或打包后的 `ERP自动化.exe`，不再要求用户运行 BAT、Python 命令或旧脚本。程序把领星官方 OpenAPI 能力、定制订单规则、自动标发队列、SQLite 状态管理、加密配置和跨电脑迁移集中到一个界面中。

当前版本优先使用领星官方 API；联系方式因需要在同一详情页写入电话和买家邮箱并做保存后读回校验，固定使用原网页流程。旧脚本不会与新程序并行运行，发布时仅保存在经过最终业务规则验收的 Git 回退分支中。

## 日常使用

### 直接运行 EXE

将整个 `dist\ERP自动化` 文件夹放在当前 Windows 用户有写权限的位置，然后双击：

```text
dist\ERP自动化\ERP自动化.exe
```

不要只复制其中的 EXE，也不建议放到需要管理员权限才能写入的目录。程序会在 EXE 所在目录维护 `data`、`rules`、`logs` 和浏览器 Profile。网页专用步骤默认调用系统 Chrome；首次遇到登录、验证码或二次验证时，需要用户在打开的浏览器中完成验证，程序不会绕过网站安全校验。

### 第一次启动

1. 新电脑首次启动时，程序先通过公开 GitHub 清单校验并更新自身；确认程序为最新版后，再导入获准的加密 `.erp-client` 授权文件。授权不绑定某一主机，但必须按公司访问凭据保管。
2. 程序优先复用本机尚未过期的 Cloudflare Access 会话，不会在后台或启动时自行打开网页。只有会话缺失或过期时，程序才会先显示说明弹窗；用户点击“打开网页登录”后，才使用本人 `@billyprint.com` 邮箱接收 OTP。ERP Access 应用会话应配置为 Cloudflare 支持的最长 1 个月。验证通过后，界面和日志中的操作者身份由服务器签名校验结果确定，不能由客户端自填。
3. 打开“设置”，为当前登录邮箱填写或导入领星、阿里国际站、Amazon 和通知服务配置；不同邮箱账号的设置彼此隔离。
4. 确认订单文件夹、浏览器 Profile 和“ERP 仓库/物流 ID 映射”，选择分阶段出库或快速出库。业务 SQLite 和队列只保存在服务器。
5. 点击“保存加密配置”，再点击“测试领星 API”。测试只执行无副作用的订单读取，用于验证 Token、签名和连接。
6. 初始状态会“紧急停止所有 ERP 写入”。先完成只读扫描并检查候选数据，确认配置正确后，再使用左侧全局按钮解除写入急停。

主界面包含：

- “仪表盘”：查看等待、运行、成功、需人工处理和已取消任务，并显示每项任务的可信企业邮箱操作账号。
- “定制订单”：后台每 5 分钟扫描一次 Amazon 待审核订单，只有没有自定义订单标签的订单才会进入定制候选；也可点击“立即扫描”。已经入队且尚未完成的订单如果在下一轮完整候选快照中消失，程序只会对无错误订单核对对应付款月份的订单文件夹：找到文件夹则自动收口为已完成，未找到则保持或恢复为待处理；存在最后错误、人工复核锁或人工阻止阶段的订单完全保留原状态，必须由用户手动处理。快照不完整或文件夹根目录不可访问时也不会据此改状态。可按平台单号、系统单号或商品类型搜索；按复选框批量处理勾选订单，查看或修改阶段状态，并可从指定阶段重新打开工作流。联系方式、订单文件夹、SKU、拆包和说明书备注分别拥有自己的待处理状态；已完成阶段会在下次处理时直接跳过。
- “自动标发”：在线客户端自动选出一个临时调度主实例；只有它按服务器保存的 3 小时到期时间提交领星“待审核”整表扫描，并在需要时打开本机可见 Chrome 查询到期的阿里国际站物流记录。主实例关闭、休眠、断网或登录失效后，其他在线客户端会自动接替且不会重置扫描周期；人工点击始终由点击者本人执行并记入日志。扫描不检查付款时间，也不会在扫描阶段写入 ERP。阿里出现登录、验证码或安全验证时，操作者可直接在本机 Chrome 中处理；没有在线客户端时不会在 VPS 上无头读取，物流记录保持待查询。表格直接显示阿里物流单号、国际物流单号、承运商、中文处理状态和中文标发进度；只有复选框勾选的安全订单才会按表格顺序进入单线程标发队列。
- “阿里物流下单”：输入领星系统单号或平台单号后，程序先唯一定位领星系统订单，再读取详情并按 SKU 识别产品分类；当前只开放帐篷顶 SKU。一个平台单号对应多个系统订单时会停止并要求明确选择，绝不猜测。地址默认读取领星 OpenAPI；若 OpenAPI 地址不完整，则复用提交任务电脑上已登录的 Chrome Cookie，通过后台只读接口读取并核对同一系统单号，不额外打开领星页面，也不保存地址副本。第一步只打开阿里查价页，不自动选择或填写任何查价字段；程序在当前客户端临时显示发货地“中国大陆 / 佛山市”、目的国家和标准化邮编，并提供邮编一键复制；这些临时查价资料不写入任务日志或共享持久化记录。操作者在阿里页面人工选择发货地、目的国家，粘贴邮编，再填写包裹尺寸、重量、件数并选择线路。程序随后重新读取并填写收货地址、帐篷申报资料、平台客户订单号及可选签收服务。加急勾选必须与 Expedited/加急线路一致，但“加急订单”和“需要签收服务”是两个互不绑定的独立选项。美国 ZIP+4 取前 5 位，加拿大邮编转为大写并保留中间空格。DDP 线路固定申报 USD 800。程序只填写并逐项回读校验草稿，绝不自动点击查价或最终下单。
- “状态管理”：查看后台任务、操作账号、能力实际模式和 ERP 写入急停状态；后台任务支持勾选后批量安全取消。全局急停只保留在左侧固定入口。
- “设置”：编辑当前登录企业邮箱账号的服务器加密配置、测试 API，并导出或导入加密的客户端授权与该账号设置。
- “日志”：无需额外账号或权限即可查看简洁的任务结果；表格、完整应用日志以及新生成的定制订单/自动标发扫描审计文件都会记录由服务器验证的操作账号。定制订单和自动标发页面分别打开各自的详细扫描日志目录，也可以按任务 ID 查看完整扫描审计文件。日志页可在二次确认后删除 1 个月或 3 个月以前的日志，清理范围严格限制在工作区 `logs` 目录。

后台任务按功能使用独立 Worker：定制扫描、自动标发扫描、客户通知扫描以及三类业务执行可以并发推进；定制订单处理、ERP 自动标发和客户通知各自在自己的单 Worker 队列中按提交顺序领取任务，客户通知批次内部最多并发发送 5 条。急停会取消尚未开始的写任务；已经进入原子步骤的任务不会被强制杀死，但会在下一次写入边界重新检查急停并停止。后台仍有任务时不能解除急停。

所有手动队列操作都必须填写原因。重试、取消、恢复、人工完成和撤销会追加不可静默覆盖的事件历史；这些状态操作不能代替领星 ERP 写入，也不能绕过全局急停、订单身份核对和 ERP 写入前的可见确认。

关闭主窗口时，程序会自动取消尚未开始、等待确认和可协作停止的只读任务；已经获得确认并进入处理中的 ERP 写入会等待当前安全工作流完成，随后窗口自动关闭。关闭等待期间不再接受新任务。

## API 与网页能力边界

领星接口以[领星官方 API 文档](https://apidoc.lingxing.com/#/docs/TestToken/Token)为准。当前程序已接入下列官方能力：

| 业务能力 | 执行方式 | 主要官方接口 |
| --- | --- | --- |
| 获取及刷新 Token | API，自动维护 | `/api/auth-server/oauth/access-token`、`/api/auth-server/oauth/refresh` |
| 扫描订单列表 | API | `/pb/mp/order/v2/list` |
| 读取订单详情 | API | `/erp/sc/routing/order/Order/getOrderDetail` |
| 下载订单定制 ZIP | API 优先、失败后询问网页补位 | `/filestream/api/cepf/attachment/download` |
| 写回电话和买家邮箱 | 网页详情页，保存后读回校验 | 原有订单详情编辑流程 |
| 调整订单商品 | API | `/pb/mp/order/v2/updateOrder` |
| 更新客户备注 | API | `/pb/mp/order/setRemark` |
| 拆分订单或包裹 | API；业务成功且 `data.result` 完整返回全部系统单号后立即完成 | `/pb/mp/order/v2/splitOrder` |
| 查询仓库和物流方式 | API | `/erp/sc/data/local_inventory/warehouse`、`/erp/sc/routing/wms/WmsLogistics/listUsedLogisticsType` |
| 设置仓库和物流渠道 | API | `/pb/mp/order/editOrder` |
| 审核订单 | API | `/basicOpen/openapi/multiplatform/order/review` |
| 查询销售出库单 | API | `/erp/sc/routing/wms/order/wmsOrderList` |
| 写入跟踪号 | API | `/basicOpen/logisticsOrdering/setTrackingNo` |
| 发货出库 | API | `/basicOpen/selfShipmentOrder/deliveryGoods` |
| 快速出库及结果查询 | API | `/pb/mp/order/v2/fastOutbound`、`/pb/mp/order/v2/getFastOutboundResult` |

以下步骤没有合适的领星官方 API，或因写入可靠性策略保留网页实现：

| 能力 | 保留网页的原因 |
| --- | --- |
| 写回电话和买家邮箱 | 两个字段统一在订单详情页保存并最长等待 10 秒读回，避免 API 列表刷新延迟造成误判 |
| 读取未遮罩的完整收货地址 | 当前官方订单接口未提供项目所需的完整未遮罩信息 |
| 查询阿里国际站物流 | 数据属于阿里国际站，不是领星 OpenAPI 能力 |

Amazon 订单商品数量继续通过 Amazon SP-API 获取。客户发货通知由独立的 v12 审核队列管理：自动扫描只生成草稿，只有用户在“客户通知审核”页确认后才会真实调用阿里企业邮箱或 ClickSend；单条和批量发送均先在同一弹窗内预览完整邮件，旧邮件批次仅保留用于审计。

对于已被官方 API 覆盖的功能，桌面程序不会静默切回网页。读取失败后会弹窗询问是否使用保留的网页流程；拒绝后立即停止。写入只有在 API 明确拒绝且能够证明本次请求尚未执行时，才会弹窗询问是否使用网页写入。超时、断线或任何无法证明“未执行”的结果会让当前阶段保持“待处理”并加人工复核锁，禁止重复写入；下次处理时必须先选择“确认未执行，重新处理”或“确认已执行，标记本阶段完成”。关闭或拒绝复核弹窗会继续保留复核锁。

桌面任务不会再依赖 CMD 输入。联系方式、文件夹、SKU 调整、拆包以及 ERP 标发会在主窗口显示写入明细并等待确认；说明书备注已合并到拆包确认中，后续写入不再重复弹窗。任务列表在等待交互时显示“等待用户确认”。只有一个联系方式候选时，即使只包含电话或邮箱，也不再额外弹出“联系方式不完整”确认，统一由真正写入前的联系方式修改审核弹窗确认；存在多个互不相同的候选时仍需先选择，避免程序擅自猜测。弹窗中的联系方式只用于当次核对，通用交互审计只记录请求编号、阶段和选择结果，不保存电话或邮箱正文。

订单文件夹名过长时只删除完整业务片段，并把完整名称写入说明文件；平台单号、收件人姓名以及原有末尾确认片段都属于受保护内容，不会因缩短目录名而被删除。收件人姓名只使用原有的领星网页订单详情读取逻辑，API 返回的姓名不参与判断或兜底；网页详情返回 `-`、`N/A`、`null`、`未知` 等占位值时按缺失处理，并禁止创建姓名为空的新订单文件夹。日志记录网页详情最终读取到的姓名和数据来源，便于逐单追查。

帐篷说明书备注按中国大陆工作日历和北京时间 09:00–18:00 计算。普通订单取“发货时限前 1 个工作日、付款后首个可处理工作日、程序实际可处理工作日”中的最晚日期；加急订单只取付款与实际处理对应的可处理工作日。18:00 起、周末和法定节假日顺延到下一个工作日，调休上班日正常处理。规则只应用于尚未写入说明书备注的订单，已完成订单不回写。

订单扫描采用失败关闭策略。只要分页未完整结束、总数不稳定或 API 返回失败，就不会把快照声明为完整：定制扫描不会写入候选数据库，也不会返回可操作订单；自动标发不会把不完整快照中的候选写入队列，也不会据此变更已有任务。自动标发中只有单条订单缺少关键字段时，会把该订单隔离为“需人工检查”，不会阻断同一快照中的其他完整候选；当前已读取的安全统计和逐单判断仍会写入扫描审计，供排查使用。

扫描结果不会只显示一个容易误解的“新增数”：

- 定制扫描显示 API 读取订单数、规范化行数、候选数和各项 `skip_counts`。
- 自动标发界面日志分别显示服务器领星扫描和本机阿里物流查询结果；领星分页保存在自动标发扫描审计中，阿里逐单查询、状态转换和完整数量统计由独立的本机可见浏览器任务记录。
- “本次新增 0”只表示这一轮没有新增队列任务，不代表队列为空；已有等待、重试、阻塞或已完成任务仍按实际队列总数显示。

## Token、签名与加密配置

源码单机模式的可编辑配置保存在工作区的 `data/config.enc`，使用 Windows DPAPI 绑定当前 Windows 用户。正式共享客户端则按服务器验证后的企业邮箱分别保存 AES-GCM 加密配置，每个账号拥有独立的 `data/operator-config/<SHA256(email)>.enc`；订单、通知和任务队列仍是全公司共享状态。服务器不会把密码、Secret 或 Token 明文返回到桌面。设置页仅接收敏感值的实际字符数并显示等量掩码圆点；保留圆点保存不会修改原值，输入新值才会更新。每次覆盖保存会保留对应加密配置的 `.bak`，敏感值不会写入 README、Git 或普通日志。

领星 Access Token 和一次性 Refresh Token 由程序自动申请、提前刷新并原子轮换。令牌单独保存在当前用户的：

```text
%LOCALAPPDATA%\ERPAutomation\lingxing-token.enc
```

令牌文件同样使用 DPAPI，并通过进程锁避免多个请求同时消费同一个 Refresh Token。令牌密文和载荷均绑定当前 AppID/AppSecret 的域分离单向指纹：任一凭据变化或遇到旧版未绑定令牌时，都会安全忽略缓存并重新签发；文件中不保存这两项明文。用户不需要复制、粘贴或手工更新 Token；修改 AppID/AppSecret 后保存配置，下一次任务会用新的凭据建立客户端。

正式程序不再提供旧 `.env` 导入入口，也不依赖 `.env`。历史明文 `.env` 应在确认服务器加密配置可用后人工安全删除。不要把 `config.enc` 当作跨电脑备份直接复制；跨电脑使用下文的加密客户端授权文件。

## ERP 物流 routes 配置

“ERP 仓库/物流 ID 映射”按阿里物流返回的规范化承运商名称匹配领星的仓库和物流方式。程序绝不会根据名称猜测 ID；缺少映射时，该任务进入人工处理。

下面的数字和字符串均为虚构占位值，不能直接用于生产，请替换为当前领星账号通过官方仓库、物流方式接口查到的真实值：

```json
{
  "示例承运商": {
    "warehouse_id": 123456,
    "logistics_type_id": 234567,
    "fast_logistics_type_id": "示例-快速出库线值",
    "freight_currency_code": "USD"
  }
}
```

- `warehouse_id`：正整数，领星仓库 ID。
- `logistics_type_id`：正整数，分阶段审核/出库使用的物流方式 ID。
- `fast_logistics_type_id`：快速出库接口要求的原始字符串；只使用分阶段出库时可省略。
- `freight_currency_code`：可选运费币种，例如 `USD` 或 `CNY`。

推荐先使用“分阶段审核并出库”。只有确认账号的快速出库字段和值后，才切换“快速出库”。所有 ERP 写入仍受全局急停和操作确认保护。

## 业务规则

### 扫描时间范围

- **定制订单**只处理付款时间位于最近 **96 小时**内的订单。API 查询会略微放宽边界以避免开放区间漏单，业务层随后再次执行精确的 96 小时判断；不会恢复为旧版本的 24 小时窗口。
- **自动标发**扫描领星当前“待审核”整表：不限制平台，按中国时区最近 30 个自然日的购买时间读取全部分页，只要订单带有设置页“自动标发扫描标签”配置的自定义标签就进入候选判断；默认标签为“标发”，可由用户修改，完全不读取或校验付款时间。扫描同时读取“客选物流”，订单第一次进入自动标发队列的中国自然日记为第 0 天；`expedited` 在第 1 天、`standard` 在第 3 天仍没有匹配校验通过的承运商和国际物流单号时，界面显示非阻断的“物流逾期异常”供用户关注，不把任务写成错误，也不停止后续自动查询。API 查询按允许的最大区间拆窗，边界重叠的数据按领星系统订单 ID 去重。点击“扫描并查询物流”后，客户端会立即预打开一条已到期的阿里物流页，让登录或安全验证与服务器领星扫描并行；服务器扫描进入终态后，再自动查询本轮新增和所有已到重试时间的历史阿里物流记录。即使领星扫描失败，仍会继续本机物流查询。若客户端在领星扫描完成前离线，历史记录保持待查询，等待下次在线客户端手动查询或下一轮扫描。
- 阿里物流详情按同一表格或信息卡片内的“字段名—字段值”关系读取，不依赖固定行列位置；`ALS...` 是阿里物流订单号，不能作为国际尾程单号。查询批次复用同一个本机物流标签页，并在桌面任务中显示当前序号和物流单号；页面字段可读后不再等待持续网络请求，单个悬挂响应不会阻塞整批查询。页面尚未提供真实国际单号时保持“等待物流就绪”并按周期重查，页面标签、联系人等文案不会写入国际物流单号。
- 定制订单后台扫描周期固定为 5 分钟，自动标发扫描周期固定为 3 小时；自动标发的领星阶段在服务器执行，阿里网页阶段在发起任务的本机执行。如果同类扫描或本机阿里查询仍在等待或运行，本轮定时触发会跳过，不会重复排队。
- “买家申请取消”属于领星系统处理标签，即使主状态仍显示待审核，也会把已入队的活动定制工作流改为“不需要”。若后续两个不同的完整扫描均确认取消标签消失，且订单仍符合普通候选规则，系统只会自动恢复此前因买家取消而设为“不需要”的阶段并重新入队；快照不完整、订单消失或重新出现取消标签都会清零确认次数。用户点击处理时还会在任何写入前实时复查一次，避免两次定时扫描之间继续处理已取消订单。
- 当前范围内未出现的队列任务不会被自动判定为完成。完整快照内标签被移除时，未完成任务会自动暂停；标签重新添加后，只恢复这类自动暂停任务并立即重试，不会重新打开已完成或手动取消的任务。

### 定制标签判定

定制候选只认领星订单级的“自定义订单标签”，不把订单状态、平台状态、系统处理提示或其他系统标签混入这一字段：

- 领星系统提示不会阻断定制候选；例如系统自动显示的处理提示不能被误判为用户自定义标签。
- 订单只要存在任何自定义订单标签，就会从自动定制候选中排除；这也包括名为“直接制作”的自定义标签。
- 如果接口缺少用于区分自定义标签和系统提示的关键字段，扫描会按快照不完整处理并失败关闭，不会猜测标签语义后继续写入。

定制扫描只覆盖 Amazon；自动标发扫描不限制平台，会覆盖当前“待审核”扫描范围内满足规则的所有平台订单。

### 3x6m 帐篷与整行替换

- 帐篷拖轮包每套固定为 `x1`；3x6m 沙袋四件套每套固定为 `x2`。多套帐篷再分别乘以套数，包括同一商品行购买多件的情况；例如同一行购买两套 3x6m 时，拖轮包为 `x2`、沙袋四件套为 `x4`。
- 主商品行用于替换配件时，必须整行替换，不能只替换其中一部分。
- 替换后的配件数量等于该主商品行最开始的数量。例如原商品行数量为 3，替换行数量也必须为 3，而不是最多替换 1 个。
- 当配件总需求不足以覆盖完整商品行时，该行不做部分替换；剩余配件需求使用新增商品行承接。

该语义同时保留来源订单行 ID、原始 SKU 和原始数量，用于 API 写入前匹配与写入后核对，防止把配件写到错误订单行。

## SQLite 状态与旧 JSON 迁移

新程序使用两个可持久化状态库：

```text
data/automation.sqlite3       # 定制订单、阶段状态、事件历史和查重
data/shipment_queue.sqlite3   # 自动标发队列、物流/ERP 检查点及保留的历史邮件记录
```

用户不需要直接打开数据库。在“定制订单”和“自动标发”页面可以查看当前状态；定制订单的各阶段状态操作统一收在“更多批量操作 → 修改状态”级联菜单内。修改定制阶段、从阶段重开、重试自动标发阶段或取消任务时，都必须填写原因并保留审计历史。定制流程因用户拒绝、急停或普通错误中断时，只暂停当前阶段，不回退此前已完成阶段；`已阻止/BLOCKED` 只允许用户手动设置。

定制订单、自动标发和客户通知这三类自动化功能，其业务规则升级后的历史结果由服务器共享控制器统一重判，而不是由某个界面单独修复。程序启动、设置切换或对应状态库发生变化时，会先重判旧版自动规则造成的可证明误判，再生成这三类自动化功能共用的最新状态。阿里物流下单、状态管理、设置和日志不执行此类业务重判。自动重判只恢复为待处理或待重新查询；人工判定、已完成阶段、已发送通知和已经执行的 ERP 写入均保持不变，并记录规则迁移日志。

“自动标发”页面还允许用户按订单身份手动添加队列任务，并以中文业务状态显示物流查询与 ERP 标发进度。勾选单条订单后，可以通过“更多批量操作 → 修改物流单号和承运商”保存或更正真实尾程信息；此功能不限制 JYC 或其他物流单号前缀，保存时仍遵守自动标发的状态与并发安全校验。保存会校验承运商和物流单号、保留人工审计记录，并将资料完整的订单转为可标发，但不会立即写入 ERP 或发送客户通知。物流状态只有在阿里状态可处理、承运商有效、国际单号匹配且费用与重量完整时才会进入“可标发”；异常资料进入人工复核。界面只提供受控状态变更：重试、取消、恢复、人工完成和撤销人工完成；每次操作都记录操作者、原因、前后状态和时间。人工完成只改变本地工作流判定，不能伪造领星 ERP 已写入，也不会跳过真正执行 ERP 标发时的急停检查和写入确认。

服务器的正式状态已经统一迁入 SQLite，设置页不再显示“状态迁移预检”或“JSON 迁入 SQLite”。只有维护历史源码工作区时，管理员才可离线执行一次性迁移；迁移实现仍会：

1. 先生成带时间戳的 `processed_platform_orders.json.pre_sqlite_*.bak`；
2. 在 SQLite 事务中导入，失败则整笔回滚；
3. 保留原 JSON 和备份，不做隐式双向同步。

自动标发数据库的 schema 升级也会在原文件旁生成对应的升级前备份。不要在桌面程序运行期间使用第三方 SQLite 工具直接改库。

## 客户端授权与设置导入/导出

设置页只保留“导出设置与授权”和“导入设置与授权”两个入口。导出会生成 `.erp-client` 文件，其中包含：

- 连接固定阿里云服务器所需的受限 SSH 私钥、固定主机指纹和协调服务 Token；
- 由服务器创建的配置专用 `.erp-migrate` 加密包，不包含两个 SQLite、队列、日志或其他业务状态。

外层和内层都使用至少 12 个字符的密码，经 Argon2id 派生密钥并用 AES-GCM 加密和认证。文件不绑定某一台主机，可在新电脑安装公开客户端后直接导入；也可在首次启动窗口中手工选择 SSH 私钥、主机指纹并填写协调 Token。导入覆盖前会保留 `.bak`。

业务队列和 SQLite 始终只在服务器保存，因此不再迁移状态，也不会因为多台电脑导入同一授权而各自产生一份队列。`.erp-client` 文件和密码合在一起等同于公司系统访问权，必须分开通过可信渠道传递；密码无法找回。文件明确排除 `.env`、浏览器 Profile、日志、调试截图、虚拟环境和生成输出，新电脑仍需按需完成领星或阿里网页登录。

## 客户通知和日志策略

- 自动标发扫描会采集联系方式和全部包裹并生成本地审核草稿，但不会自动对外发送；只有“审核通过并发送”会调用供应商。历史邮件批次不删除、不改写，也不影响 ERP 标发完成判定。
- 日志页面不增加应用内访问权限，当前电脑用户可直接查看简洁的状态、时间、任务 ID、结果摘要和安全错误编号；文件仍受 Windows 自身的文件权限保护。
- 每次 API 定制或标发扫描都会生成一个与桌面任务 ID 一一对应的完整审计文件；两类队列分目录保存，文件名包含电脑本地时区的扫描开始日期时间：

  ```text
  logs/custom_order_scan/YYYY-MM-DD/custom_order_scan_YYYYMMDD_HHMMSS_<task_id>.json
  logs/shipment_scan/YYYY-MM-DD/shipment_scan_YYYYMMDD_HHMMSS_<task_id>.json
  ```

  两个队列页面只打开各自的目录；日志页仍可按任务 ID 查询新目录及旧版 `logs/api_scan` 中的历史文件。文件记录 schema/version、扫描类型、起止时间、经过服务端验证的操作账号、安全查询摘要、分页轨迹、逐单决定、数量原值及规范化结果、汇总统计和 `error_id`；不会保存原始 API response 正文。
- 成功结果会显示 `error_id=无`；异常结果保留原始业务异常消息和安全错误编号，便于按任务 ID 对照完整审计。异常堆栈仍不捕获局部变量、请求正文或源码表达式，消息中的认证凭据继续过滤。
- `logs` 和 `debug/logs` 中超过 90 天的日志文件会在程序启动时清理，扫描审计同样执行固定 90 天（三个月）保留策略；程序拒绝把其他名称的宽泛目录当作自动清理根目录，避免误删普通文件。
- 本地业务日志固定保留原始诊断值且不做业务字段脱敏，包括姓名、邮箱、电话、收货地址、定制内容、文件夹完整名称及被删除片段；这样历史订单可以按日志逐项复盘。AppSecret、Token、账号密码、Authorization/Cookie 和带签名查询参数的临时 URL 仍属于认证凭据，不会明文写入；原始 API response 正文仍不整包落盘，只记录业务流程实际消费的字段。为了责任追溯，会保留经过服务端验证的公司操作账号邮箱。任务 ID 只允许安全文件名字符，日志路径拒绝目录穿越、符号链接和 Junction 穿越。

## 严重错误时回退

新程序不在运行时维护旧、新两套入口。脚本回退版已经冻结并可用于受控回退：

```text
分支：codex/script-fallback-20260714-v2
固定提交：40254237447ae1ae36f02cbfa16e65110bdb0e3d
基线测试：596 passed
```

该固定提交包含定制订单付款窗口 96 小时和整行替换数量规则，但也包含已经废弃的“3x6m 拖轮包 `x2`”规则，因此不能用于本次配件数量规则回退。旧的 `codex/script-baseline-20260714` 仍是 24 小时语义且缺少最终整行数量规则，同样禁止直接用于本次发布回退。

可变业务数据的回退快照位于 `rollback_backups/rollback_时间戳`，每份快照包含 `manifest.json`、文件是否原本存在、大小和 SHA-256。恢复前会先验证所有哈希；目标已有文件还会保留一份 `.pre_restore.bak`。快照只允许工作区内普通文件，不接受符号链接或越界路径。

如果出现严重错误，请先退出桌面程序，然后明确要求维护者/Codex“回退到脚本基线”。标准顺序是：

1. 对当前 `config.enc`、SQLite、旧 JSON、日历和规则创建新的 `rollback_backups` 快照；
2. 在仍使用重构代码时，通过 `CustomWorkflowStore.export_legacy_json` 把当前 `automation.sqlite3` 的最新完成/忽略状态导出成脚本兼容的 `processed_platform_orders.json`，并校验导出数量；不能直接拿 14:11 的旧快照覆盖最新查重状态；
3. 核对 `codex/script-fallback-20260714-v2` 的固定提交哈希和上述三项验收清单，保留当前重构分支和提交，再切换到该回退分支；
4. 恢复刚导出的兼容 JSON，以及脚本版本需要的配置/日历/规则，验证订单查重状态后再运行。

不要在程序仍运行或数据库仍有写入任务时直接切分支，也不要把“切换代码分支”误当作“自动恢复业务数据”。旧 BAT/脚本只用于这条受控回退路径，不是新版本的日常启动方式。

## 开发环境

项目要求 Windows；源代码至少需要 Python 3.11，当前开发环境建议使用 Python 3.14。安装依赖：

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

如电脑没有可供 Playwright 调用的 Chrome，可为源码调试安装 Chromium：

```powershell
.\.venv\Scripts\python.exe -m playwright install chromium
```

从源码启动桌面程序：

```powershell
.\.venv\Scripts\python.exe desktop_main.py
```

也可临时指定一个独立、可写的运行目录，避免开发测试接触正式状态：

```powershell
$env:ERP_AUTOMATION_HOME = "$PWD\smoke-workspace"
.\.venv\Scripts\python.exe desktop_main.py
Remove-Item Env:ERP_AUTOMATION_HOME
```

主要代码目录：

- `erp_automation/ui/`：PySide6 页面、桌面状态模型和持久化控制器。
- `erp_automation/application/`：桌面任务、API 扫描、能力路由、定制订单 API 和 ERP 标发编排。
- `erp_automation/integrations/lingxing/`：鉴权、Token 轮换、签名、端点策略和异步 HTTP 客户端。
- `erp_automation/configuration/`：DPAPI 配置、`.env` 导入和便携迁移加密。
- `erp_automation/persistence/`：定制订单 SQLite 工作流与事件历史。
- `lingxing_automation/`：产品规则、文件夹生成、定制解析，以及仅无 API 步骤所需的网页适配器。
- `shipment_automation/`：自动标发队列、阿里物流查询与下单草稿规则、ERP 检查点和保留的历史邮件兼容代码。

这些模块由桌面 Worker 在同一进程中调用，不会通过 BAT 或子进程启动旧脚本。

```powershell
.\scripts\finalize_release.ps1 -ExpectedExeSha256 "<正式 EXE 的 64 位 SHA256>"
```

执行报告保存在 `rollback_backups/retention_reports`。桌面程序或使用项目 `browser_profile` 的自动化浏览器仍在运行、SQLite 完整性异常、路径越界、存在符号链接/Junction、正式 EXE 哈希不一致或业务归档验证失败时，工具会安全停止。
# 客户发货通知与销售出库单选择（数据库 v12）

自动标发扫描会在同一平台单号的全部本地队列任务达到 `DONE / OUTBOUNDED`
后，从领星 WMS 读取全部包裹并生成待审核通知。扫描只采集数据、重扫空白物流和
生成新版本，不会自动调用阿里邮箱或 ClickSend。

- 客户邮件中的物流单号按面单来源逐包裹选择：人工填写物流使用 WMS
  `waybill_no`，系统获取面单使用 `tracking_no`。优先使用 WMS 物流提供商中的
  `手动- / manual-` 来源标记；仓库只作为来源字段缺失时的辅助证据，默认仓不再
  自动等同人工填写。来源无法确认且两列内容不一致时，整个平台订单停止发送并进入
  人工复核；来源已确认但目标列尚未生成时继续等待，不按单号格式猜测或静默换列。
- 客户通知按包裹以领星 WMS 数字状态为准：只有 `status=3` 且最终物流完整的包裹
  可进入当前审核；同平台订单中仍为等待、未知或尚无最终物流的其他包裹继续留在
  扫描范围，不得用预发货运单号推断已出库，也不得进入本次通知。
- 同一系统单号存在多条销售出库单时，系统停止自动写入并要求用户明确选择
  `wo_number`；选择会保存到 v11 队列中，每次写入前重新校验，检查点推进后禁止换单。
- WMS 状态为 `4 / 已截单` 的历史销售出库单不会进入人工候选；若当前只有已截单记录，
  标发流程按“尚无有效销售出库单”继续审核并等待领星生成新单。新单与旧截单记录同时
  返回时只处理新单；任何未知状态仍会阻止写入，禁止猜测。
- 定制 ZIP JSON 是通知邮箱和电话的优先可信来源；联系方式一经选定就立即保存，即使 ERP
  联系方式此前已写回或后续文件夹/SKU 阶段失败也不会丢失。用户也可在“客户通知审核”页
  勾选未发送通知后点击“从定制 JSON 获取联系方式”，程序会在订单日期对应的本地文件夹中
  查找并校验平台单号完全一致的定制 JSON，再更新本地草稿。JSON 缺失、歧义或解析失败时
  不猜测、不调用领星订单详情接口，也不会清空原有有效值。该操作不写 ERP，不发送邮件或短信。
- 收件人姓名只从 WMS 的 `consignee`（兼容明确的姓名别名）读取；WMS 邮箱和地址字段被忽略。
  只有当前可发送包裹返回唯一且能规范化的收件电话时，才把该电话保存为 WMS 电话候选；姓名
  为空、为占位符或同一订单出现冲突姓名时禁止审核发送，电话存在多个不同有效值时也禁止猜测。
- 真实有效邮箱使用阿里企业邮箱；Amazon 平台虚拟邮箱禁止发邮件，但销售出库包裹返回唯一且
  格式有效的收件电话时直接改用 ClickSend 短信，不再因缺少匹配的定制 JSON 电话而降级为
  “需人工发送邮件”。虚拟邮箱且没有可用电话时才保留人工邮件状态；邮箱、电话都不可用时
  进入“待补联系方式”，禁止审核发送。
- 订单列表中的系统单号只描述扫描范围，不会合成客户包裹。只有 WMS 已返回真实
  `wo_number` 的非 Instruction、非终止、非冲突记录才进入客户包裹总数；其中尚未出库或
  尚无最终物流的真实包裹计入总数但不进入本次物流明细。因此三个真实包裹中两个已出库时
  生成 `2/3` 草稿，正文只列两个可发送单号；WMS 尚未返回任何包裹记录的系统单不会形成
  虚假的 `1/2`。全部真实包裹尚未就绪时继续等待，不生成错误草稿。
- 客户正文只列出 `status=3` 且物流完整的真实信息，不显示预发货单号或占位物流行；审核页
  的包裹进度显示“已有可发送物流/已确认真实包裹总数”。
- 最近 30 天 Amazon 补偿扫描不再用主图字段判断是否入队：包含领星人工创建/拆分商品行
  （没有 `product_no/asin` 平台商品身份）的订单进入补偿队列；带平台商品身份的原始 Amazon
  商品行不会因为 `data_json.snapshot_image` 缺失而误入队。SKU 为 `Instruction` 时无条件触发
  补偿入队，不受平台商品身份或主图字段影响。商品名称只保留标题第一个 `|` 或 `｜` 前的内容。
  SKU 为 `Instruction` 的系统单可提供
  商品名称，但其物流包裹仅在审核表中置灰显示，不计入客户包裹数，也不会进入邮件或短信。
  没有可靠主图标题或同一系统单混有 Instruction 与实物 SKU 时显示“待补商品信息”并禁止发送。
- 邮件和短信均按稳定字母显示 `Package a / Package b`。邮件审核快照保存带物流单号
  超链接的 HTML；短信在每个完整包裹后附加一行 HTTPS 查询地址。FedEx、UPS、USPS、
  DHL 和 GOFO 使用预填单号的落地页，其余承运商安全回退至 17TRACK。
- 物流补齐、修正或新增包裹会生成包含全部新旧物流的最新内容：尚未批准或发送的部分草稿
  原地更新（例如 `2/3` 更新为 `3/3`）；部分通知已经发送后再补齐时，创建新的 `3/3`
  revision 并同时列出旧单号和新单号，等待再次人工审核。已经发送的物流不会因 WMS 临时遗漏
  而消失。标发完成回调、三小时扫描、自动标发页
  手动扫描、人工核对物流并放行和通知页手动同步共用同一只读补偿逻辑，均只生成或更新
  待审核草稿，不会自动调用外部发送接口；通知页人工同步会包含仍处于后台重试退避期的
  订单，避免已经补齐的 WMS 包裹继续滞留；服务器也会忽略旧客户端遗留的自动发送标记。
- 通知列表按每页 50 条从服务器读取轻量摘要，单击或进入发送审核时才按需读取包裹、正文和
  审核历史；历史已发送、已完成和已取消记录仍保留。列表读取失败时保留上次成功数据并明确
  显示失败，不再用空数组伪装成“没有通知”。列表显示平台单号、收件人、邮箱、电话、包裹进度、
  北京时间状态时间、状态和“状态说明”，可按全部字段或指定字段搜索。列表采用单元格选择；当前格或多个所选格可用
  `Ctrl+C` 或右键菜单复制。“人工完成”和“已取消”统一从“修改状态”进入；页面不再常驻
  显示邮件正文，完整邮件统一在发送审核弹窗中逐条预览。渠道、编码、分段、内部版本等幂等
  字段继续保存在数据库中但不在审核界面展示。
- 对外发送的唯一入口是桌面端“客户通知审核”页的“审核通过并发送”；可批量勾选，
  WMS 出库状态在扫描进入审核列表前统一校验；发送阶段不再重复查询 WMS，
  但每条仍独立校验审核指纹和幂等键，批量任务最多并发发送 5 条；
  供应商接收后由协调服务在后台持续查询送达回执。人工重开会保留旧通知和回执，
  新建 revision 后再次等待审核。
- 发送服务接收每条通知后，协调服务在后台持续轮询最终状态，桌面端不占用发送任务等待回执。
  阿里邮箱通过发送历史查询，
  ClickSend 短信通过 `/v3/sms/history` 按精确 `message_id` 查询，不依赖可选的 POLL
  回执规则。确认成功后标记“已完成”；供应商明确失败时标记“发送失败可重试”；
  查询连续失败或期限内状态未更新时标记“状态核验失败”，并明确说明这不等于发送失败，
  防止用户误点重试导致重复发送。“刷新发送状态”可继续补查这些记录。真实发送 RPC 的
  读取超时按通知条数扩展，连接和写入仍使用短超时，避免服务器已经完成批量发送而桌面端
  在固定 30 秒后误报失败。

阿里邮箱 App ID/Secret、两个发件邮箱、ClickSend Username/API Key 和可选 Sender
ID 均保存在 `data/config.enc` 的 Windows DPAPI 加密文档中。设置页只以密码框显示
Secret/API Key，并提供不发送消息的连接测试。任何曾经出现在聊天或其他明文位置的
生产 Secret/API Key 都应在上线前轮换，再通过设置页保存新值。

## 多人共享与服务器部署

多人使用时，不能把两个 SQLite 文件直接放到 SMB 共享目录，也不能让每台电脑各自运行
后台 Worker。正式模式由 Linux 服务器运行唯一的协调服务，Windows 程序只保留界面并通过
SSH 隧道调用服务器控制器：

- 服务器统一保存订单状态、通知、任务队列和审计日志；业务队列是全局唯一的，设置则按经过
  Cloudflare 验证的企业邮箱分别加密保存。一个账号修改自己的账号、密码或 API 凭据不会覆盖其他账号。
- 每个窗口注册独立实例，并绑定服务器验证后的操作者姓名、邮箱和 Cloudflare subject。
  订单写入、状态修改和审核日志都记录该可信身份，客户端提交的显示名不能替代登录身份。
- 所有写操作按订单、物流单、通知、配置或功能取得服务器租约；同一实例的不同请求也不能顶掉
  已持有的租约。冲突时会显示占用操作者，任务终止或租约超时后自动释放。
- 后台业务编排由服务器按功能划分独立的单 Worker 通道；不同扫描、扫描与业务执行、以及定制处理、自动标发、客户通知三类执行可以并发，同一功能内仍按队列顺序领取任务，客户通知批次内部最多并发发送 5 条。队列、数据库和写入租约只有一份。需要网页的任务
  绑定到提交任务的桌面实例，并通过该实例的反向 SSH 通道连接本机可见 Chrome；登录、验证码和
  阶段审核不会转移到其他电脑静默执行。
- 在线客户端自动选出一个临时调度主实例，只有它提交 5 分钟和 3 小时定时扫描。调度租约失效时
  其他在线客户端自动接替；服务器持久化下次到期时间，接替不会造成重复扫描或重置周期。
- 状态修改、扫描进度、审核结果和错误都会增加共享 revision。桌面客户端每秒读取一次 revision；
  内容没有变化时服务器不重复传输快照，有变化时所有在线客户端都会刷新共享队列。
- 只读 RPC 不写入协调幂等缓存；写操作仍保存响应以防重复执行。升级启动且确认没有恢复中的
  活动任务时，服务器会在不阻塞健康检查的后台维护中清理旧版只读响应并执行完整性校验；释放的
  SQLite 页面会供后续写入复用，避免数据库继续膨胀，正式启动不再等待整库备份或 `VACUUM`。
- API 只监听服务器 `127.0.0.1:18765`，不直接暴露公网；客户端通过 SSH 本地端口转发，并同时
  提交至少 32 字符的 Bearer Token 和 Cloudflare Access 签名 JWT。服务器固定校验 issuer、audience、
  有效期、RSA 签名和精确的 `@billyprint.com` 域。
- Linux 配置使用服务器独立的 256 位 AES-GCM 主机密钥；主机密钥、API Token、Cloudflare audience、
  每账号加密配置、业务数据库和一次性旧配置归属标记均位于 Git 仓库之外。

服务器运行文件位于 `deploy/server/`。Debian 11 主机通过 Docker 运行固定版本的
Playwright Ubuntu 镜像，因为当前 Playwright 已不再把 Debian 11 列为直接支持的宿主系统。
首次安装使用：

```bash
sudo bash /srv/lingxing-erp-automation/repo/deploy/server/provision_debian.sh
sudoedit /etc/lingxing-erp/cloudflare-access-audience
sudoedit /etc/lingxing-erp/bootstrap-operator-email
```

完成初始化后，正式上线不再直接运行服务器内部脚本。应在已经审核并同步
`origin/main` 的 Windows 工作区依次运行
`.\scripts\publish_client_release.ps1 -ConfirmProductionRelease` 和
`.\scripts\deploy_production.ps1 -ConfirmProductionDeployment`。部署入口只接受本机授权的
精确 main 提交 SHA 与客户端版本；服务器若在切换前检测到活动任务会拒绝部署，待任务结束后
重新执行即可。

生产部署私钥固定保存在本机 NTFS 目录
`%LOCALAPPDATA%\Codex\credentials\erp-production-deploy-ed25519`，部署脚本显式调用
Windows OpenSSH，并使用同目录的 `erp-production-known_hosts` 固定服务器指纹。群晖目录
`Z:\同事个人\颜奕超\ERP自动化部署专用` 只保存公钥、`known_hosts` 和绑定当前 Windows
用户的 DPAPI 加密备份，不保存可直接使用的明文私钥。本机凭据丢失时可显式运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File `
  .\scripts\restore_production_deploy_credentials.ps1 -ConfirmCredentialRestore
```

恢复脚本拒绝覆盖现有凭据，并会核对解密私钥与公钥备份是否匹配；所有 Codex 任务只能调用
私钥完成受限部署，不能读取、打印、复制、提交或上传私钥内容。

`cloudflare-access-audience` 必须是本应用的 Access AUD tag；`bootstrap-operator-email` 必须只含一个
完整的 `@billyprint.com` 邮箱，用于把现有 `data/config.enc` 一次性分配给该账号。首次分配后服务器
保存邮箱 SHA256 归属标记，修改引导邮箱也不会再次复制旧凭据。其他账号首次登录后填写或导入自己的设置。

### 本机测试运行

日常改动不再发布候选版本。关闭已安装的正式客户端后，直接双击仓库根目录的
`start_local_test.cmd`，即可运行当前分支源码；原来的 `start_shared_desktop.cmd` 也会转到
同一个本机测试入口。命令行等价用法是：

```bat
start_local_test.cmd
```

本机测试同时显示两个版本：`CLIENT_VERSION` 是当前源码准备发布的下一正式版本，正式连接基线则是
这台电脑已经安装并通过服务器门禁的正式版本。例如正式版为 `2026.08.06.2` 时，待验收源码可以是
`2026.08.06.3`，但测试会话仍以 `2026.08.06.2` 完成服务器兼容性登记；这不代表 `.3` 已经发布。

该入口只允许运行源码，不安装或更新 EXE，也不读取 GitHub 正式更新清单。本机可写状态固定放在
`%LOCALAPPDATA%\LingxingERP-LocalTest`，不会覆盖正式客户端的本地配置和状态库。为了显示真实订单，
启动器会复用当前电脑已经授权的正式访问文件和企业邮箱浏览器 Profile，通过受控的本机 SSH 隧道
连接已部署的正式协调服务；访问令牌只由启动器读取到进程内存，不会复制到测试目录或写入日志。

测试窗口标题、侧栏和橙色横幅会持续显示“本机测试”，并明确提示订单来自正式业务环境。当前分支
只替换客户端源码，服务器仍是已部署版本；因此客户端界面、交互和远程调用可以直接实操，服务器
代码改动仍需依靠自动化测试及正式部署后的单机上线冒烟覆盖。处理订单、标发、发送通知等写入会
影响真实业务数据，必须按正式操作标准审核。正式版与本机测试不得同时运行，启动脚本检测到正式
EXE 或另一测试实例时会拒绝继续。

日常流程固定为“功能分支 → 针对性测试 → 本机测试运行并实操 → 拉取最新 `main` → PR 与完整 CI →
正式发布 → 服务器部署 → 本机正式版更新与上线冒烟”。不再创建 GitHub prerelease，不再安装第二套
候选客户端，也不再提供正式版/候选版选择窗口。

## Windows 客户端下载包

正式客户端以单目录 EXE 压缩包发布，不包含 SSH 私钥、API Token、真实配置、数据库、日志或
订单文件。构建后运行：

```powershell
.\scripts\package_shared_client.ps1 `
  -BuiltApplicationDir "$PWD\release-staging\dist\ERP自动化" `
  -Version (Get-Content CLIENT_VERSION -Raw).Trim() `
  -ArchiveName "ERP-Automation-Client.zip"
```

本项目定位为公司内部客户端：更新结构采用常见桌面软件的版本目录、完整性校验、失败保留旧入口
和自动切换流程，但不作为面向公众销售的软件发布。当前不配置 Windows 商业代码签名证书，因此
下载安装时 Windows 可能显示“未知发布者”，不同版本也不会继承 SmartScreen 发布者信誉；这不
影响下述 HTTPS、不可变 Release 地址、SHA256、内容树校验、防回退和服务器版本门禁。

生成的 ZIP 包含 EXE、兼容旧版本的共享启动器、安装脚本和更新器。解压后运行安装脚本；它会
先在隔离临时数据目录运行 EXE 启动自检，通过后才安装到当前用户的
`%LOCALAPPDATA%\Programs\LingxingERP\<版本>` 并创建桌面快捷方式；自检失败时不会留下程序
入口。安装包不会生成、下载或内置任何公司授权。新电脑首次启动时，EXE 先通过公开清单完成
程序更新；随后必须在 SSH 连接和服务器数据读取之前导入 `.erp-client` 或手工填写授权材料，
取消或材料缺失时直接停止，不能进入公司系统。手工解压安装后的第一次更新检查会使用正式清单复核完整内容树、修正外部
`VERSION.txt` 元数据并补写安装收据，因此之后与自动更新安装处于相同状态且不会重复下载。

桌面快捷方式只指向正式 EXE，不再携带服务器地址、Token、实例名或其他启动参数。EXE 自己
完成更新检查、SSH 隧道、服务器认证、本机浏览器通道和实例注册，不再通过共享启动器二次
启动程序；启动器只保留给已经安装的旧客户端完成跨版本升级。直接双击项目或安装目录中的
EXE 与点击桌面快捷方式会进入同一条阿里云队列、实例锁和实时刷新流程。
正常启动时，客户端先静默检查更新；检查与连接在 0.75 秒内完成时不显示启动窗，只有启动确实
较慢时才显示统一的卡片式进度窗，避免短暂闪出系统默认样式窗口。

客户端版本号在构建时固化进 EXE。运行时只使用该内置版本，不读取或依赖客户端目录中的
`VERSION.txt`，因此该文件缺失、滞后或被误改都不会造成重复更新或阻止 EXE 启动。发布 ZIP
仍包含 `VERSION.txt` 作为安装包元数据，并必须与受信任的正式发布清单一致；不一致的安装包会
被拒绝。这样既避免外部版本文件造成运行故障，也不允许旧 EXE 跳过正式更新。

同一版本在不同电脑上的正式安装目录应与发布 ZIP 的全部文件逐项一致；更新清单保存整个 ZIP
内容树的确定性 SHA256，客户端只有在逐文件重算结果一致时才复用已安装版本。项目源码目录还包含
源码、测试、Git 元数据和本机构建产物，不属于正式客户端镜像，也不应与安装目录整体相同。
当用户在旧的项目 EXE 中确认更新后，更新器会复用已校验的正式安装版本，并在旧进程退出后
原子接替该 EXE 入口；即使旧入口位于 Git 项目中，也只替换 `dist` 客户端和已有版本标记，
绝不覆盖源码、测试、配置、业务数据或未提交文件。普通非 Git 便携目录还会同步发布包内的五个
更新脚本。便携副本的替换使用暂存、备份和提交标记；断电发生在目录切换中间时，下次更新会先
恢复旧副本再重试。后续再次双击同一路径不会重复下载。Codex 不会在发布流程外手工替换用户的
本机 EXE。

正式客户端始终通过以下固定地址发布：

- 下载包：`https://github.com/Steven-BillyPrint/lingxing-erp-automation/releases/latest/download/ERP-Automation-Client.zip`
- 更新清单：`https://github.com/Steven-BillyPrint/lingxing-erp-automation/releases/latest/download/latest.json`

安装了更新器的客户端会在建立 SSH 隧道前检查清单。存在新版时只能立即更新或退出；网络检查
失败时，仅当最近 24 小时已经成功确认本机是最新版才允许继续。更新器固定只接受对应版本的
不可变 GitHub Release 地址，并校验下载大小、ZIP 路径、展开大小、文件 SHA256 和完整内容树；
本机一旦确认过更高版本，也会拒绝清单回退。临时网络故障最多自动重试三次，并在下载前检查
磁盘空间。已经运行的客户端如果在服务器兼容窗口结束后才收到强制更新响应，会在窗口内启动同一
套校验更新；新版本写入独立目录后，旧窗口先注销实例并关闭 SSH/浏览器隧道，随后才启动新 EXE。
同一版本的失败响应只提示一次，不会每秒重复弹窗；服务器返回空白或异常版本号时不会下载未知版本。

新版先完整写入同盘暂存目录，再以目录重命名提交到独立版本目录；同版本损坏修复也不会就地混合
覆盖。安装完成后再次校验内容树，并用隔离的临时数据目录运行打包 EXE 冒烟自检；自检完成后还
会再次复核安装收据和内容树。只有这些步骤全部通过，才原子替换桌面快捷方式；任一步失败时旧
快捷方式和旧版本仍可使用。并发启动的多个
客户端共用更新互斥锁，等待者会复用第一个客户端已经校验的安装，不会重复下载。系统保留当前版
和一个最近旧版，清理更早且未被进程使用的版本及超过 24 小时的事务残留。SSH 密钥、Token、
浏览器 Profile、账号配置和业务数据位于版本目录之外，更新不会覆盖。
VPS 还会核对客户端版本，非 `CLIENT_VERSION` 指定的正式版本不能注册共享实例。

`main` 的 `Tests` 工作流会并行运行完整测试与 Windows 客户端构建；客户端构建任务还会完成
打包 EXE、安装器及更新器冒烟测试，并把只属于该精确提交的已验证发布资产保存为短期 Artifact。
发布由 GitHub Actions 的 `Build client release` 手动工作流完成。发布脚本只接受当前精确
`main` SHA 对应的成功 `push` CI Run，并把 SHA、CI Run ID 和一次性请求 ID 传给工作流。
发布工作流会通过 GitHub API 再次核验仓库、受信任工作流、分支、事件、提交和成功结论，从该
Run 下载已验证发布资产，重新计算 ZIP SHA256、内容树和清单后才创建草稿 Release；不会重复运行完整
测试或重新构建客户端。即使工作流排队期间 `main` 又前移，发布资产仍只来自获准的精确 SHA；
管理员确认后先把 Release 资产公开但不标记为 GitHub `latest`，因此固定下载地址仍指向
上一版。随后部署相同 `main` 提交的服务器并通过健康检查；新服务器先进入“等待更新入口
激活”状态，无限期兼容上一正式版本，并保持部署排空锁、不接收新的后台写入任务。部署脚本
确认 GitHub `latest` 已切换到该 Release 后，才通过受限部署命令把持久 `pending` 标记原子
替换为绝对截止时间、重启无任务的协调服务并开放新任务。此后才开始 15 分钟兼容窗口。
如果 GitHub 激活或最终确认失败，旧客户端仍可连接，服务器不会提前开始倒计时；重新运行部署
脚本会根据服务器回执幂等续做。部署排空锁没有自动超时，只能由验证成功的最终激活或完整回滚
显式解除；最终确认仍会在同一数据库事务内重新检查活动任务。激活重启或健康验证失败时，服务
会恢复为 `pending` 兼容状态并保留排空锁，绝不为启动倒计时而重启正在执行任务的服务。
新于服务器、缺失或格式异常的版本始终拒绝。兼容窗口结束时，上一版本若仍拥有活动任务，只能
继续读取状态、响应该任务的人工审核或取消该任务，不能再提交新任务；租约释放后的下一次刷新
才触发安全更新。因此长时间停留在本机网页审核的任务不会因版本窗口到期而被切断，也不能借此
无限延长旧版写入权限。排空期间如果网络中断超过实例心跳时限，客户端会使用原实例 ID 自动
重新注册并继续同一任务；没有活动任务的过期旧版不能借重新注册绕过更新门禁。
如果服务器已经健康而 GitHub `latest` 切换失败，受限部署密钥只能读取服务器保存的提交、
版本和健康回执；下次运行部署脚本会核对对应的正式 Release 后幂等补做激活，即使此时
`main` 已经前移也不会丢失恢复路径。发布和部署均拒绝把更新通道回退到更低版本。
正式部署先在旧服务继续运行时构建候选容器；最终切换时持有协调数据库写锁，检查所有活动
写操作，并在同一个锁周期内停止旧服务。任何后台任务仍在执行、等待人工审核或刚提交尚未
绑定任务号时都会拒绝部署，因此不会出现“检查结束后又启动一项任务”的竞态。候选容器只有
通过版本和健康检查才提交。切换前会把容器镜像、协调环境文件、三个 systemd 单元、
Cloudflared、滚动版本文件和部署回执保存到 root-only 持久事务目录；普通错误或断电后再次
运行时都会恢复完整旧环境。新服务的提交回执和持久 `committed` 标记写入后才允许进入上述
更新入口激活阶段；存在待激活滚动版本时，事务目录可以安全提交清理，但部署排空锁继续保留，
直到更新入口和滚动截止时间都确认成功，因此不会在已经接收新任务后误回滚。协调服务在线期间，
后台任务租约只在任务明确进入终态时
释放，不能仅因时间超时、状态刷新失败或客户端短暂断网而消失；部署门禁会把这些租约全部视为
活动任务。协调进程重启时后台 Worker 已不存在，因此新进程只清除上一进程遗留的孤儿任务租约。
空闲客户端的实例租约和本机 Chrome 反向通道端口保存在协调数据库中，服务器重启后会恢复；
已经打开的上一版本按上述规则完成在途任务，新启动的程序则必须先完成更新。

客户端授权只允许发给获准人员；不要共用可写 GitHub 凭据。服务器仓库使用只读 Deploy Key
拉取 `main`，日常代码链路为“本机分支 → GitHub PR/合并 → 服务器
`fetch` + `merge --ff-only` → 重建容器 → 健康检查”。服务器不向 GitHub 推送代码。

服务器生成的订单文件通过 Docker 绑定到群晖目录
`Public/Amazon每日订单汇总`，容器内路径仍为 `/runtime/outputs`。服务器通过专用账号和
SFTP 端口 `42875` 将群晖根目录挂载到 `/mnt/lingxing-nas`。主机密钥固定在
`/etc/lingxing-erp/nas-sftp-known_hosts`，密码保存在
`/etc/lingxing-erp/nas-sftp-password`；密码文件必须保持 `root:root` 和 `0600`，
不得写进 Git 仓库、systemd 单元或命令行参数。

`lingxing-nas-sftp.service` 使用 SSHFS 自动连接、断线重连并严格校验固定的主机密钥。
协调服务显式依赖该挂载，并在启动前检查挂载点和目标目录；NAS 不可用时服务拒绝启动，
避免文件意外写回服务器本地磁盘。Docker 只绑定目标子目录，不向应用暴露 NAS 的其他共享目录。
