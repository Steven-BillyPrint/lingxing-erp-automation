# 自动标发扫描与复查复用物流浏览器

此前已经将普通物流查询和历史复查分成两个任务，但任务交接仍有三处会打断页面连续性：Worker 结束时关闭物流页；客户端看到任务结束后清空物流浏览器的所有页面；新任务提交时再次打开 SCM 首页。保留磁盘上的浏览器 Profile 并不能保留被关闭页面的 sessionStorage，也不能避免重新打开页面触发的登录检查。

这次保留独立调度、普通任务优先、历史资格缓存和限流，调整浏览器生命周期：

- 桌面拥有的物流浏览器在任务间保持打开。Worker 只停止本任务的 Playwright 连接，保留浏览器上下文、物流页、Cookie 和 sessionStorage；客户端不再按物流任务的结束状态清空页面。
- 新任务优先使用已有 SCM 或登录/验证页面，不重新导航首页。冷启动、用户关闭页面或没有可复用页面时，才打开 SCM 首页并执行原有登录流程。
- 浏览器仍按当前桌面实例和物流专用 Profile 隔离，不借用阿里下单浏览器。沿用配置账号变更核验与精确订单身份校验；账号变更时停止复查，要求重新登录。
- 登录过期、验证码和页面故障仍执行原有处理，浏览器技术故障保留一次受控恢复。退出客户端关闭保留的物流浏览器。CLI 自己启动的浏览器仍按原有规则清理。

回归测试覆盖真实 Chromium 的两个独立 CDP 连接生命周期：先执行普通查询，处理终态快照，再独立提交历史复查，确认只有原来的一个页面，Cookie 和 sessionStorage 保持不变，历史查询确实执行。另一个场景在交接时修改配置账号，确认复查以 `identity_mismatch` 停止，没有记录成功复查。

测试页面全部由本地拦截响应提供，不访问真实阿里或 ERP。另覆盖冷启动、原页缺失、登录重定向、域名隔离、成功/失败/暂停/取消后的页面保留、驱动资源释放和客户端退出清理；这些回归同时进入 Windows 全量测试和服务器 Python 3.12 检查。

此修改减少我们主动关闭页面、重开首页引起的额外登录机会，不能保证阿里不再要求验证。正式使用需要按仓库流程发布客户端和服务器，并通过内置更新器升级客户端。
