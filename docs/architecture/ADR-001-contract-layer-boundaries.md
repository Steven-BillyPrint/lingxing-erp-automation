# ADR-001：公共契约层与模块依赖边界

- 状态：已接受
- 日期：2026-08-25

## 背景

桌面任务命令、快照、设置、交互和控制器协议原本定义在
`erp_automation.ui`。应用服务和协调服务需要共享这些类型，因此反向依赖
UI，导致无界面服务端也必须了解桌面层的模块结构，并放大跨层改动范围。

## 决策

系统继续采用模块化单体，不为解决进程内耦合引入微服务。新增
`erp_automation.contracts` 作为桌面端、应用层和协调层共享的稳定契约边界。

- `contracts.models` 是公共枚举、常量和数据传输对象的权威定义。
- `contracts.controller` 是控制结果和后台控制器协议的权威定义。
- 契约层只能依赖 Python 标准库或契约层自身模块，不执行 I/O，也不实例化
  UI、数据库或外部服务。
- 应用层和协调层不得直接导入 UI。UI 可以依赖契约层和应用层。
- 跨 UI、服务端和后台任务共享的新数据结构必须先在契约层定义。

本次迁移不改变枚举值、字段、默认值、方法签名、任务 payload、RPC JSON、
数据库结构或客户端入口。`erp_automation.ui.models` 和
`erp_automation.ui.controller` 保留为无警告的兼容导出，并指向相同的类型
对象。

## 兼容与后续清理

旧 UI 导入入口只有同时满足以下条件后才可以移除：

1. 仓库内部调用全部使用契约层入口；
2. 至少经历一个稳定正式发布周期；
3. 已验证没有外部插件或已发布客户端依赖旧模块路径。

协调服务启动入口和离线迁移入口目前仍通过 `erp_automation.app` 获取组合根；
这是已知后续任务，不在本次契约搬迁中改变。控制器接口分面、强类型任务命令
和 RPC 注册表也属于后续任务。

## 结果

无界面应用和协调代码不再依赖 UI 公共模型；架构测试会阻止反向依赖回归。
代价是一个发布周期内需要维护旧入口的薄兼容层，但不会形成两套类型或双向
转换。
